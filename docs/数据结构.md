# 数据结构与 Schema

> 基座：AgentScope 2.0.x（Agent Service + Web UI），PostgreSQL 16 + pgvector，Redis（AgentScope message bus）。
> AgentScope API 迭代较快，标注「待核对」的条目需在实现时对照实际安装版本确认。

## 0. 总览

### 设计原则

1. **数字不经过 LLM**：财务数值从 EDGAR XBRL 结构化入库，经确定性代码计算、渲染，全程不进入 LLM 的生成路径。
2. **事实落库，消息自描述**：agent 之间的消息里，LLM 需要读的内容（摘要、状态）直接写在消息中；数据本体用引用传递（claim-check 模式）。
3. **闭集约束计算，开集承载事实**：三张 registry 是闭集，用来约束口径、计算和校验；fact 长表是开集，非标准指标也能存进去。
4. **会话归 AgentScope，业务归我们**：对话上下文和消息历史由 AgentScope storage 托管，我们只定义业务表，通过 `session_id` / `msg_id` 关联过去。

### 存储布局

| 位置 | 归属 | 内容 |
|---|---|---|
| PG `public` schema | AgentScope（Alembic 维护） | sessions、messages、agents、teams、knowledge_bases 等 |
| PG `fin` schema | 本项目 | registry、事实、文档、任务、产物、记忆 |
| Redis | AgentScope | message bus：会话锁、事件回放、team 消息 |
| 文件系统 | 本项目 | 原文缓存（source_documents.local_path）、产物文件（xlsx/csv） |

用独立的 `fin` schema，是为了避免和 AgentScope 的 `sessions` / `messages` 等表名冲突。

### 溯源链

```
xlsx 单元格
  → task_artifacts.meta.cells（cell → fact_ids）
  → fact_financials（值、单位、期间、accession、XBRL concept）
  → source_documents（原文 URL、本地缓存）
  → EDGAR 原始申报
```

全程在同一个 PG 库内，用 SQL join 即可串起来。

### 表关系

```
company_registry ─┬─< fact_financials >── source_documents ──< doc_chunks
metric_registry ··┘        ▲   (metric 列按 registry 映射，可为空)
source_registry            │
                           │ (fact_ids, JSONB)
task_runs ─┬─< run_coverage
           ├─< run_steps ·····> AgentScope sessions / messages
           └─< task_artifacts
agent_memory ·····> task_runs (source_run_id)
```

## 1. Agent 间消息契约

以 pydantic 模型定义，作为 worker agent 回复的结构化输出。

worker 的调用方式还没定，有两个选项：
- Agent Team：消息是文本，契约需要序列化后放进 TeamSay
- 把 worker 封装成编排 agent 的工具：契约可以强类型

**倾向后者（待定）**。理由是流程固定（采集 → 报表 → 分析），不需要 leader 动态组队。

### 1.1 DataRequest（编排 → 数据获取 agent）

```python
class DataRequest(BaseModel):
    run_id: str                       # 任务逻辑 id，覆盖结果和流水都挂在它上面
    user_query: str                   # 用户原文，不做 LLM 改写
    companies: list[str]              # 已标准化的 ticker；"上次那家公司"之类的指代在编排层已解析
    metrics: list[str] | None = None  # 用户指定的展示指标；None 表示使用偏好集或核心集
    period: tuple[date, date]         # 日期区间（含两端）
```

说明：
- 不包含输出格式、财季/日历季对齐等渲染参数，这些属于报表工具。
- `metrics` 不参与覆盖自检，自检只核对公司 × 期间（见 run_coverage）。它只用来限定 web 兜底时搜索的范围。

### 1.2 DataResult（数据获取 agent → 编排）

```python
class DataResult(BaseModel):
    run_id: str
    status: Literal["complete", "partial", "failed"]
    summary: str                      # 给编排 LLM 读的摘要，如"AAPL/MSFT 2024Q1–2025Q2 已入库 12 份申报；NVDA 2025Q3 尚未申报"
    counts: dict[str, int]            # {"covered": n, "low_confidence": n, "missing": n}
```

明细都在 `fin.run_coverage` 里，消息中不重复。

### 1.3 build_table（报表工具，确定性，不调用 LLM）

```python
def build_table(
    run_id: str,
    metrics: list[str],                               # 展示指标（registry 键）
    alignment: Literal["fiscal", "calendar"] = "fiscal",
    format: Literal["xlsx", "csv", "md"] = "xlsx",
) -> TableResult: ...

class TableResult(BaseModel):
    artifact_id: str
    summary: str                      # 给 LLM 读：表格维度、缺失格数量、低置信格数量
    preview_md: str                   # 表格的 markdown 预览（仅用于展示，数字仍以文件为准）
```

处理流程：读取 fact → 选取 concept（按 registry 优先级）→ 计算派生指标（含 Q4 = 全年 − 前三季累计）→ 渲染文件并逐格挂溯源 → 写入 task_artifacts。

### 1.4 AnalysisRequest / AnalysisResult（编排 ↔ 分析 agent）

```python
class AnalysisRequest(BaseModel):
    run_id: str
    user_query: str
    table_artifact_id: str | None = None   # 有表格时，叙述要引用其中的单元格

class AnalysisResult(BaseModel):
    run_id: str
    artifact_id: str                  # 叙述已写入 task_artifacts(kind='narrative')
    text: str                         # 叙述全文，直接返回给编排层
    citations: list[Citation]
    warnings: list[str]               # 缺失、低置信等需要用户注意的事项

class Citation(BaseModel):
    span: tuple[int, int]             # text 中的字符区间
    ref_type: Literal["cell", "fact", "chunk"]
    ref: str                          # "<artifact_id>#数据!C5" | fact_id | chunk_id
```

分析 agent 的工具：`query_facts(run_id, ...)` 和 `search_knowledge`（RAGMiddleware 的 agentic 模式提供）。约束是 cite-or-abstain：数字只能引用表格或 fact 中已有的值，找不到依据就不说。

## 2. 闭集：Registry

三张表都是配置数据，用种子脚本初始化，运行时只读。

### 2.1 company_registry：公司标准化与范围限定

明确列出覆盖范围（限定行业），并负责名称标准化和财年对齐。

```sql
CREATE TABLE fin.company_registry (
  company        TEXT PRIMARY KEY,            -- ticker，如 'AAPL'
  cik            TEXT NOT NULL UNIQUE,        -- SEC CIK，10 位补零，EDGAR API 主键
  name_official  TEXT NOT NULL,               -- 官方全称
  aliases        TEXT[] NOT NULL DEFAULT '{}',-- 别名（'苹果'、'Apple Inc.'），名称标准化的映射来源
  fy_end_month   SMALLINT NOT NULL
                 CHECK (fy_end_month BETWEEN 1 AND 12),  -- 财年截止月（AAPL=9），用于财季标签计算
  sector         TEXT NOT NULL,               -- 所属行业，如 'mega-cap-tech'
  ir_domain      TEXT                         -- 官方 IR 域名，用作 web 兜底的白名单
);
```

### 2.2 metric_registry：指标口径

统一口径，并支撑派生指标展开和两级数据质量。存的是数据不是代码，新增指标只需加一行。

```sql
CREATE TABLE fin.metric_registry (
  metric        TEXT PRIMARY KEY,             -- 标准指标键，如 'revenue'、'gross_margin'
  kind          TEXT NOT NULL
                CHECK (kind IN ('base','derived')),
  period_type   TEXT NOT NULL
                CHECK (period_type IN ('duration','instant')),  -- 利润表/现金流量表为区间值，资产负债表为时点值
  xbrl_concepts TEXT[],                       -- base：候选 concept，按优先级排列（公司打 tag 的习惯不同，tag 也会废弃）
  formula       TEXT,                         -- derived：基于 base_metrics 的表达式
  base_metrics  TEXT[],                       -- derived：展开时依赖的基础指标
  unit          TEXT NOT NULL,                -- 'USD' | 'USD/shares' | 'shares' | 'pure'
  is_core       BOOLEAN NOT NULL DEFAULT false, -- 用户未指定指标且无偏好时的默认集
  definition    TEXT NOT NULL                 -- 口径说明
);
```

### 2.3 source_registry：数据源策略

数据源的优先级和可信度，决定数据获取 agent 的降级顺序：本地 → 官方 API → web。

```sql
CREATE TABLE fin.source_registry (
  source_id    TEXT PRIMARY KEY,              -- 'sec_edgar_xbrl' | 'sec_edgar_submissions' | 'web_search'
  source_type  TEXT NOT NULL
               CHECK (source_type IN ('official_api','web')),
  endpoint     TEXT,                          -- API 模板，如 data.sec.gov/api/xbrl/companyfacts/CIK{cik}.json
  applies_to   TEXT[],                        -- 适用公司；NULL 表示全部
  priority     SMALLINT NOT NULL,             -- 越小越优先
  trust_level  TEXT NOT NULL
               CHECK (trust_level IN ('verified','unverified')),  -- 直接决定 fact 的 confidence
  notes        TEXT                           -- 如"必须带 User-Agent（应用名+邮箱），限速 10 req/s"
);
```

## 3. 事实层

### 3.1 fact_financials：财务事实长表（K/V）

每行是一个带完整溯源的数据点，同时也是溯源的最小单元；渲染时 pivot 成宽表。

```sql
CREATE TABLE fin.fact_financials (
  fact_id       BIGSERIAL PRIMARY KEY,
  company       TEXT NOT NULL REFERENCES fin.company_registry,
  concept       TEXT NOT NULL,                -- 原始概念：XBRL 'us-gaap:Revenues'；web 抽取为 'web:<指标名>'
  metric        TEXT REFERENCES fin.metric_registry,  -- 入库时按 registry 映射出的标准指标；未映射为 NULL
  period_start  DATE,                         -- instant 类指标（资产负债表）为 NULL
  period_end    DATE NOT NULL,
  value         NUMERIC(24,4) NOT NULL,       -- 精确小数；存源单位原值，不做量级缩放
  unit          TEXT NOT NULL,                -- 沿用 XBRL 单位：'USD' | 'USD/shares' | 'shares' | 'pure'
  form          TEXT,                         -- 来源申报类型：'10-Q' | '10-K' | '8-K'
  frame         TEXT,                         -- SEC 按日历期间去重的标记（如 'CY2025Q2'），有则优先采用
  source_type   TEXT NOT NULL
                CHECK (source_type IN ('xbrl_api','web_llm','manual')),
  source_ref    TEXT NOT NULL,                -- EDGAR accession number 或 URL
  doc_id        TEXT REFERENCES fin.source_documents,  -- 有原文缓存时关联
  filed_at      DATE,                         -- 申报日；同一期间被重述时，取最新一条
  retrieved_at  TIMESTAMPTZ NOT NULL,
  confidence    TEXT NOT NULL
                CHECK (confidence IN ('verified','low')),  -- 只表示来源可信度，由 source_registry.trust_level 决定
  UNIQUE NULLS NOT DISTINCT (company, concept, period_start, period_end, source_ref)  -- 幂等入库；不同来源可以并存
);
CREATE INDEX ON fin.fact_financials (company, metric, period_end);
```

说明：
- **两个独立的维度**：`confidence` 表示来源是否可信；`metric IS NULL` 表示不是标准口径。官方数据未必是标准口径，标准口径的数据也可能来自 web。
- **不存 companyfacts 的 `fy`/`fp` 字段**：它们标的是所在申报的财年和期间，不是这个数据点本身的期间（比如 10-Q 里的上年同期对比数，也会带上本期的 fy）。财季标签统一由日期加 `fy_end_month` 推导。
- **3 个月和 9 个月累计会并存**：同一份 10-Q 里，同一个 `period_end` 会有这两种区间长度的 fact，取数时按区间长度区分。
- **派生指标不落库**：毛利率、Q4 单季值这些都由报表工具现算。
- registry 更新后，可以用一条 UPDATE 重新映射 `metric` 列。

### 3.2 source_documents：原文档案

原文的元数据和本地缓存，是"核对原始来源"的落点，也是叙述 RAG 的文档来源。

```sql
CREATE TABLE fin.source_documents (
  doc_id          TEXT PRIMARY KEY,
  company         TEXT NOT NULL REFERENCES fin.company_registry,
  doc_type        TEXT NOT NULL,              -- '10-Q' | '10-K' | 'press_release' | 'web_page'
  period_end      DATE,                       -- 文档覆盖的期间
  url             TEXT NOT NULL,
  accession       TEXT,                       -- EDGAR 申报号（有则填），和 fact.source_ref 对应
  fetched_at      TIMESTAMPTZ NOT NULL,
  local_path      TEXT NOT NULL,              -- 原文缓存路径，Web UI 里"查看原文"打开的就是它
  checksum        TEXT,                       -- 原文指纹，判断缓存是否失效
  trust_level     TEXT NOT NULL,              -- 白名单判定结果：'verified' | 'unverified'
  kb_document_id  TEXT,                       -- 对应 AgentScope 知识库中的文档 id；索引状态由 AgentScope 管理
  extracted_at    TIMESTAMPTZ                 -- web_llm 抽取已完成（幂等标记，避免重复抽取产生不一致数字）
);
```

### 3.3 doc_chunks：向量切块（自定义 PgVectorStore）

AgentScope 没有内置 pgvector，需要继承 `VectorStoreBase` 实现 `PgVectorStore`，这张表由它读写。列结构跟随 `VectorRecord` 的契约（待核对）。

```sql
CREATE TABLE fin.doc_chunks (
  chunk_id     TEXT PRIMARY KEY,
  collection   TEXT NOT NULL,                 -- 知识库 collection
  document_id  TEXT NOT NULL,                 -- AgentScope 文档 id（= source_documents.kb_document_id）
  chunk        JSONB NOT NULL,                -- AgentScope Chunk 序列化：文本、section、页码等
  metadata     JSONB NOT NULL,                -- {company, period_end, doc_type}，供 metadata_filter 按公司和期间过滤
  embedding    vector(1536) NOT NULL          -- text-embedding-3-small
);
CREATE INDEX ON fin.doc_chunks USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON fin.doc_chunks (collection, document_id);
```

`PgVectorStore` 要实现：`create_collection` / `delete_collection` / `has_collection` / `insert` / `delete` / `search` / `list_documents`，以及 `__aenter__` / `__aexit__`。其中 `metadata_filter` 要翻译成 SQL WHERE 条件。

## 4. 任务层

层级关系：`user → session（AgentScope 对话窗口）→ run（一次用户请求）→ steps（LLM / 工具调用）`

### 4.1 task_runs：任务主表

一次用户请求对应一行，只记录任务本身。过程记在 run_steps，产出记在 task_artifacts。

```sql
CREATE TABLE fin.task_runs (
  run_id       TEXT PRIMARY KEY,
  session_id   TEXT NOT NULL,                 -- 编排 agent 所在的 AgentScope session
  user_id      TEXT NOT NULL,                 -- 来自 Agent Service 的 X-User-ID
  user_query   TEXT NOT NULL,                 -- 用户原文
  status       TEXT NOT NULL
               CHECK (status IN ('running','succeeded','partial','failed','interrupted')),
  phase        TEXT NOT NULL
               CHECK (phase IN ('collecting','tabulating','analyzing','done')),  -- 中断恢复：跳过已完成阶段
  data_request JSONB,                         -- DataRequest 快照；仅凭 run_id 恢复，不依赖编排 agent 记忆
  error        TEXT,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  finished_at  TIMESTAMPTZ,
  heartbeat_at TIMESTAMPTZ                    -- 崩溃判定：心跳过期的 running 任务被标记为 interrupted
);
CREATE INDEX ON fin.task_runs (user_id, created_at DESC);
```

### 4.2 run_coverage：覆盖报告

数据获取 agent 自检的结果，粒度是公司 × 申报期间，不细到指标。应有的申报清单由公司财年和 EDGAR submissions 接口确定性算出；指标级的缺失交给报表工具在单元格上标注。

```sql
CREATE TABLE fin.run_coverage (
  run_id      TEXT REFERENCES fin.task_runs,
  company     TEXT REFERENCES fin.company_registry,
  period_end  DATE,                           -- 应有申报的期间截止日
  form        TEXT,                           -- '10-Q' | '10-K'
  accession   TEXT,                           -- 实际匹配到的申报；missing 时为 NULL
  status      TEXT NOT NULL
              CHECK (status IN ('covered','low_confidence','missing')),
  attempts    SMALLINT NOT NULL DEFAULT 0,    -- 补采次数落库，重试上限跨崩溃有效
  reason      TEXT,                           -- 如 '尚未到申报期' | '仅 web 来源'
  PRIMARY KEY (run_id, company, period_end, form)
);
```

### 4.3 run_steps：执行流水（索引 + 指标）

由自定义的 `RunStepsMiddleware` 写入（实现 `on_model_call` / `on_acting` / `on_compress_context` 三个 hook），通过 `create_app` 的 middleware factory 挂到每个 agent 上。

这张表只记指标，不存消息内容；内容在 AgentScope 的 `messages` 表，用 `session_id` + `msg_id` 关联。某次调用时模型实际看到的上下文，可以用"messages 历史 + compress 事件"还原。

```sql
CREATE TABLE fin.run_steps (
  step_id     BIGSERIAL PRIMARY KEY,
  run_id      TEXT REFERENCES fin.task_runs,  -- NULL：UI 直接闲聊（尚无任务）；编排层任务开始时经 contextvar 设置
  seq         BIGINT NOT NULL,                -- 进程内到达顺序，用于轨迹回放
  actor       TEXT NOT NULL,                  -- 'orchestrator' | 'data_agent' | 'analysis_agent'
  session_id  TEXT NOT NULL,                  -- 该 actor 的 AgentScope session
  msg_id      TEXT,                           -- 对应的 Msg，内容去 AgentScope messages 表查
  step_type   TEXT NOT NULL
              CHECK (step_type IN ('llm','tool','compress')),
  name        TEXT NOT NULL,                  -- 模型名 / 工具名
  tokens_in   INT,                            -- llm 专有（来自 ModelCallEndEvent）
  tokens_out  INT,
  cost_usd    NUMERIC(10,6),                  -- token 数 × 价格表
  latency_ms  INT,                            -- 在 hook 包裹前后计时
  detail      JSONB,                          -- compress：压缩摘要；tool：参数摘要；error：异常信息
  status      TEXT NOT NULL CHECK (status IN ('ok','error')),
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (run_id, seq)
);
```

run_id 通过 `contextvars` 传递，编排层在任务开始时设置。

### 4.4 task_artifacts：产物

一个任务的所有产出：表格文件和叙述文本。逐格溯源以 JSONB 形式存在 meta 里，不单独建表。

```sql
CREATE TABLE fin.task_artifacts (
  artifact_id  TEXT PRIMARY KEY,
  run_id       TEXT NOT NULL REFERENCES fin.task_runs,
  kind         TEXT NOT NULL CHECK (kind IN ('table','narrative')),
  format       TEXT NOT NULL,                 -- 'xlsx' | 'csv' | 'md' | 'text'
  path         TEXT,                          -- 文件类产物（相对产物根目录）
  content      TEXT,                          -- 文本类产物
  meta         JSONB NOT NULL DEFAULT '{}',   -- 结构见下
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (run_id, kind)                       -- 重跑任务复用产物而非生成重复行
);
```

`kind='table'` 时的 meta：

```json
{
  "metrics": ["revenue", "gross_margin"],
  "alignment": "fiscal",
  "cells": [
    {"cell": "数据!C5", "kind": "extracted", "fact_ids": [1023]},
    {"cell": "数据!C9", "kind": "computed",  "fact_ids": [1023, 1188], "formula": "(revenue - cogs) / revenue"},
    {"cell": "数据!F5", "kind": "computed",  "fact_ids": [2001, 2002], "formula": "FY - 9M_YTD"},
    {"cell": "数据!D7", "kind": "missing",   "reason": "公司未披露该指标"}
  ]
}
```

`kind='narrative'` 时的 meta：

```json
{
  "citations": [
    {"span": [120, 135], "ref_type": "cell",  "ref": "art_01#数据!C5"},
    {"span": [210, 260], "ref_type": "chunk", "ref": "chk_8812"}
  ],
  "warnings": ["NVDA 2025Q3 尚未申报"]
}
```

说明：
- fact 行是不可变的（重述会产生带新 `source_ref` 的新行），所以 `fact_ids` 锁定了这次产出实际用的数字，日后重新打开报表，数字不会变。
- xlsx 里的单元格批注和"溯源" sheet，都由 `cells` 生成。

## 5. 记忆

### 5.1 agent_memory：用户画像与纠错

这是自进化机制的落点。用结构化表而不是 AgentScope 的 long-term memory（ReMe/Mem0），是因为偏好需要被确定性地查询，比如覆盖自检的默认指标集。对 agent 暴露为 `memory_read` / `memory_write` 工具。

```sql
CREATE TABLE fin.agent_memory (
  memory_id      TEXT PRIMARY KEY,
  user_id        TEXT NOT NULL,
  kind           TEXT NOT NULL
                 CHECK (kind IN ('preference','watchlist','correction')),
  key            TEXT NOT NULL,               -- 如 'preferred_metrics' | 'last_companies' | 'fiscal_alignment'
  value          JSONB NOT NULL,
  source_run_id  TEXT REFERENCES fin.task_runs,  -- 记忆从哪次任务产生，保证记忆可解释
  updated_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (user_id, kind, key)
);
```

- `preference`：常用指标、对齐方式、输出格式偏好
- `watchlist`：关注的公司，用于解析跨 session 的"上次那家公司"
- `correction`：用户纠错记录（如"这个口径应该用 X"），是体现"随时间适应用户"最有说服力的部分

同一 session 内的指代由 AgentScope 上下文自然处理，不经过这张表。

## 6. AgentScope 托管部分（不由本项目定义）

| 组件 | 用途 | 关联方式 |
|---|---|---|
| `AsyncSQLAlchemyStorage` → `sessions` 表 | 每个会话一行，记录中含 `AgentState`（下次调用实际使用的上下文，可能已被压缩） | `task_runs.session_id`、`run_steps.session_id` |
| `AsyncSQLAlchemyStorage` → `messages` 表 | 每条 Msg 一行；thinking、tool call、tool result 都是 Msg 内的 block | `run_steps.msg_id` |
| `knowledge_bases` / `knowledge_documents` 表 | 知识库和文档的索引状态 | `source_documents.kb_document_id` |
| `RedisMessageBus` | 会话锁、事件流回放、team 消息 | — |

配置：`agentscope[sql]` + `asyncpg`，连接串 `postgresql+asyncpg://...`；表结构由 AgentScope 自带的 Alembic 迁移维护。

## 6.1 DDL 落地方式

- `fin` schema 的全部 DDL 在 `backend/finagent/schema.sql`，幂等（`IF NOT EXISTS`），由 `python -m finagent.migrate` 在后端容器启动时执行（`asyncpg` 简单查询协议支持多语句脚本）
- `db/init.sql` 仅做首次卷初始化所需的两件事：`CREATE EXTENSION vector`（需超级用户）和 `CREATE SCHEMA fin`
- 本文各表定义与 `schema.sql` 保持同步，改动需双侧更新

## 7. 评估资产（文件，不建运行时表）

golden 集以 YAML 放在仓库 `eval/golden/` 下，纳入版本控制。评估脚本逐题调用 harness，每题产生一个 run_id，再按 run_id 查询产物、覆盖和流水来打分，最后输出 markdown 报告。

```yaml
- id: cmp-001
  category: comparison          # retrieval | comparison | domain_edge | adversarial | memory | summary
  query: "对比 AAPL 和 MSFT 最近四个季度的营收和毛利率"
  expected:
    cells:                      # golden 值从原文（财报新闻稿、10-Q 正文）手工核对，不能取自 companyfacts，否则是循环验证
      - {company: AAPL, metric: revenue, period_end: 2025-06-28, value: 94036000000, tolerance: 0}
    missing: []                 # 对抗题：期望系统报告缺失或弃答
  checks: [numeric_accuracy, provenance_valid, narrative_faithful, trajectory]
```

| 层 | 指标 | 数据来源 |
|---|---|---|
| L1 | 数值准确率 | task_artifacts.meta.cells ↔ golden |
| L2 | 溯源有效率 | cells.fact_ids → fact_financials → 原始来源 |
| L3 | 叙述忠实度 | narrative citations（数字做确定性比对；论断是否被支持用 LLM-as-judge） |
| L4 | 诚实弃答率 | 对抗题 ↔ run_coverage / 缺失格 |
| L5 | 轨迹与效率 | run_steps（工具选择、重试次数、tokens、成本、延迟） |
| — | 可复现性、对比 ChatGPT | 同题跑多次；同一套题交给 ChatGPT |
