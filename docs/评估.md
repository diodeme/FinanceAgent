# FinanceAgent 与原生 Codex 的小规模对照评估

评测日期：2026-10-15。代码基线：`7627848cfe0ab2d5eb9efdcdeb6311713a1ae21b`，随后进行了两轮局部修复。所有运行保留，不覆盖失败、退化或中间版本。

## 结论先行

本轮共设计 **5 道题，执行 18 次任务**：Codex 基线 5 次，FinanceAgent 初始 3 次、第一次修复后 5 次、第二次修复后 5 次。每次任务最多 300 秒。

- 最终两组的 **148 个必需数值单元格、44 个季度截止日期全部匹配独立标准答案**。这不表示全文没有数字错误：解释中的额外比率、期间描述和因果判断另行评分。
- 五题的助手分析评分均值为 **Codex 17.6/20，FinanceAgent 16.8/20**。FinanceAgent 在原三题上从 **11.3/20 提升到 15.3/20**，但仍不能声称分析质量全面超过基线。
- 观察到的平均耗时为 **112.3 秒 vs 73.1 秒**，FinanceAgent 在本次运行中约少 34.9%。但两边默认思考模式没有完全对齐，运行环境、缓存也不同，**不能把这个差值解释为仅由 harness 带来的提速**。
- FinanceAgent 输出 token 更少，输入 token 更多，不是所有成本维度都更好。没有据此估算金额。
- 最终季度经营报告仍有末尾不完整的问题，年度报告仍有额外比率错误。它们已经扣分并保留在答案快照中，不能把接口返回 `completed` 或报告已保存当成内容完整的证明。

**这是原生配置下的端到端系统比较，不是严格控制全部生成参数的 harness 消融实验。Codex 也不是 ChatGPT 产品。本轮使用 DeepSeek Flash，不能作为 GPT/ChatGPT 产品上的实测胜出证据。**

## 1. 对照设置

| 项目 | Codex | FinanceAgent |
|---|---|---|
| 配置模型 | `deepseek-flash` | `deepseek-flash` |
| 配置端点 | `api.deepseek.com` | `api.deepseek.com` |
| 凭证核验 | 来自 `.env` | 在内存核对实际服务凭证与 `.env` 一致，不输出密钥 |
| 任务输入 | 固定自然语言请求 | 完全相同的请求 |
| 检索提示/预置资料 | 不提供接口、网站指引、财报附件、golden 或项目代码 | 使用产品自己的财务能力 |
| 执行环境 | Windows，SDK 0.162.1，CLI 0.156.0 | WSL2/Linux Docker，真实 HTTP/SSE 服务 |
| 权限 | 原生 `danger-full-access` + `approval_policy=never` | 原生应用与分析工作区配置 |
| 上下文隔离 | 每题新 thread、CODEX_HOME、空工作目录 | 每题新用户、内置 agent、凭证和 session |
| 时限与重试 | 每题 300 秒，不自动重新跑题 | 每题 300 秒，超时 interrupt 并确认 idle；不自动重新跑题 |

FinanceAgent 的 SEC 数据缓存没有清空；新用户隔离历史报告，但不代表冷缓存。原生 agent 在一题内部自行重试的工具调用仍计入这题的时间和 token。

### 重要的模型配置限制

FinanceAgent 复制现有源会话的完整 `parameters={}`，不添加 4,000-token 输出上限，并禁用跨模型 fallback。后来核实，当前原生 DeepSeek 适配器的默认行为是 `thinking_enable=False`，请求显式禁用 thinking；`max_tokens=None`、`reasoning_effort=None`，输出预算取决于服务端。

Codex 使用原生默认配置，返回的 usage 包含 reasoning output tokens；没有记录可与 FinanceAgent 完全对应的显式思考档位。它还报告了 `deepseek-flash` 使用 fallback model metadata 的警告。

因此本轮确实固定了供应商端点、凭证和模型标识，但**没有完全控制思考模式与输出预算**。下一轮若要论证 harness 的独立贡献，应显式对齐这些参数，再独立重跑；不要将当前结果包装成严格受控实验。

### Gold 来源

[`eval/golden.json`](../eval/golden.json) 保存 16 个财季、4 个年度的数值、来源及计算依据：

- Apple：8 份官方 Financial Statements PDF，与对应官方新闻稿。
- Microsoft：8 份官方季度 IR 报表，以及两份官方财报电话会文本用于口径解释。
- 没有拿 SEC companyfacts、FinanceAgent 数据库或受测回答当标准答案。
- 检查单季与累计差分、全年勾稽、下一年比较列。Apple 63 项与 Microsoft 56 项源数据检查通过，统一数据再次检查各年度五项货币指标的季度合计。
- 金额为百万美元、GAAP 净利润、正向现金 PP&E 支出；FCF 为按题意计算的 OCF−现金 capex。原始官方新闻稿报表标为 unaudited，本轮没有另做完整审计。

典型核验点：Apple FY2024 Q4 的 GAAP 净利润是 14,736，不是调整后 24,982；Microsoft FY2025 Q4 的现金 PP&E 是 17,079，不是电话会中包含融资租赁的 24.2 billion。

## 3. 评分办法

规则在第一次正式运行前固定于 [`eval/rubric.json`](../eval/rubric.json)。

### 数值

从实际交付的聊天、报告卡片或明确链接的保存表格提取，保留原句/产物指针；不能用 gold 补缺项。

- 条件准确率：正确数 / 已回答数。
- 覆盖率：已回答数 / 应回答数。
- **正确覆盖率：正确数 / 应回答数**，作为主要数值指标。
- 必须匹配公司、财季、指标和单位；金额容差 0.5 百万美元，净利率容差 0.1 个百分点，比率容差 0.005。
- 未纠正的重复数值冲突不能择优计分。印刷数字匹配但单位声明矛盾，也不能计为正确。
- 在一次回归发现单位矛盾后，为 scorer 补上 `unit_conflict` 字段及测试，这是落实原有单位匹配规则，没有改变 tolerance。原始结果与冲突原文保留。

“必需单元格正确”不代表所有额外叙述正确。引用的语法及身份校验也不代表原文确实支持结论；本轮没有报告“100%溯源语义正确率”。

### 分析质量

由助手按任务覆盖、证据、财务推理、洞察与结论强度、表达清晰度五维评分，每维 0–4，总分 20。每个主要扣分附原句、位置与反例。

候选文件移除了引擎标签，但引用与版式仍可能暴露来源，因此不是严格盲评，也不是独立人工专家标注。原始评分、复评分分别保留在 [`eval/reviews/`](../eval/reviews/)，不会为了得到“修复后更好”而改旧分数。

## 5. 两轮修复及真实退化

### 初始版本

原三题必需数值 120/120，分析评分 12、11、11。主要问题：

1. 表格正确，却写“微软每季收入均增长”；FY2024 Q2 的 62,020 到 Q3 的 61,858 是反例。
2. 原文归因和极值判断存在过度概括；“数字可引用”被误当成“原因已得到证实”。
3. 年度报告两次 `invalid_citations`：引用目标都在白名单，但写成 `[#finance/…]` / `[#filing/…]`，不是标准 Markdown 链接。外层还编造“混用ID”的诊断，并在失败回退中新增错 ID。

### 第一次修复及回归

- 统一研究与渲染的完整引用格式；只对精确匹配白名单的独立短引用做确定性规范化，未知/畸形引用仍拒绝。
- 错误信息区分语法与未知目标，不把失败草稿称作已保存报告。
- 强化真实历史期间、相邻期核验及因果证据规则；明确成功报告卡片就是交付物。

**回归并非全面改善**：年度报告保存成功，但外层又把 391,035 抄成 390,035；季度经营研究完成后超过原 8,000 字符门槛，被错误归入未完成；自然年题对表格的美元/百万美元说明自相矛盾。

这一轮三原题为 48/48、48/48、23/24；两新题为 8/24、4/4。自然年题的 16 个货币值印刷正确但单位有冲突，不能择优忽略声明。所有结果保留在 `fixed` 与 `holdout` 的 FinanceAgent 快照中。

### 第二次修复及回归

- 研究交接不再重复 renderer 已收到的数值表，8k 为简洁目标；接受不超过 20k 的完整研究，空与真正超限分别报错，不截断证据。原有总研究预算与完成检查保留。
- 通过原生 `on_model_call`，只在模型请求副本中把失败分析结果投影为实际错误，避免失败草稿进入后续模型；原 UI、历史及 metadata 不变，`get_result` 和后续导出不受影响。
- 外层也遵守相邻期、极值、口径与证据约束，分析任务不能仅取数后凭空完成解释。

原三题数值恢复 120/120，分析评分提升为 15、17、14；两新题数值 28/28，分析评分 18、20。原三题报告均保存，但其中一份内容末尾不完整，**保存成功不是完整性通过**。

进一步检查确认：原成功路径本来就会压缩分析工具结果为 summary，因此不能把“成功报告正文泄漏”宣称为已确认根因；本轮真正新增的模型边界过滤针对失败草稿。外层仍可能从之前的数值上下文重新写答案，不能承诺完全消除二次改写。

## 6. 保留的不足

1. **叙述中的额外计算仍会错。** 最终年度报告将微软 FY2025 capex/营收、capex/OCF 写为约 26%、63%；由其自身表格计算应约为 22.91%、47.41%。这两个额外指标不属于 24 个指定单元格，但已在分析评分中扣分。
2. **全称趋势、期间标签仍有反例。** 现金流报告对 capex 的“逐级上升”不够准确；自然年报告正文把苹果 2024-09-28 财季误称 Q3，与正确的 FY2024 Q4 表格矛盾。
3. **一份报告末尾不完整。** 季度经营报告停在第三条结论开头。SSE 正文和保存文本逐字一致，均为 6,988 字符，排除了本地存储、规范化或 UI 切片。
4. **原生适配器丢失 provider 终止原因。** 当前 AgentScope DeepSeek 流式和非流式适配器没有保留 provider `finish_reason`，原生基类可能将流结束映射为默认 completed。该次日志只有 input_ids、phase、prompt_template、skill，无法确定是否发生 length/content_filter，不能凭句末或 token 数猜原因。此依赖问题本轮未 fork 修复；应先保留终止原因，再让 renderer 拒绝非正常结束，不能用句尾正则冒充完整性校验。
5. **输入上下文成本偏高。** 更充分地研究原文增加了输入 token；后续应在不丢证据的前提下减少重复原文和上下文，而非只优化最终回答长度。

Codex 基线也有错误，例如年度简报将两家公司财年的重叠窗口写错、解释中混淆折旧与现金支出的作用；其分析评分并非满分。

## 7. 验证、复现和证据

- 最终后端离线测试：**183 项，143 通过、40 项 opt-in 跳过**；在一次性容器中使用 `--network none`，未用这些离线测试替代真实模型运行。
- 评分器：**7 项通过**，覆盖遗漏、错误期间、重复冲突、未核验来源、单位冲突等。
- 真正的应用验证通过原生聊天 HTTP/SSE 接口，按 session 收集全部模型调用、产物与终态；不是直接调用内部计算函数。
- 每轮创建新用户/session；模型与凭证只在内存核对；没有修改 `.env` 或已有用户模型设置。
- 可复核答案、评分和原文映射见 [`eval/results/evidence/`](../eval/results/evidence/)，包含全部 18 次任务的快照。完整 SDK/原生事件日志留在本地 git-ignored `data/eval-runs/`，不发布凭证或原始模型轨迹。
- 快照中的内部引用属于测试实例；`source-map.json` 映射文档 ID 与公开原文 URL。标准答案另保留公开报表证据，不能假装离线快照本身拥有在线数据库的全部跳转能力。
- 运行命令、参数和评分流程见 [`eval/README.md`](../eval/README.md)。

本轮数据集小、同域、单次运行，没有置信区间。修复后同题回归是开发结果，两道新题也复用了相同公司/期间。**可以据此说明已发现并修复了哪些工程问题，不能据此声称全面优于 ChatGPT，或将默认模式下的速度差解释为单一架构因素。**
